02 Hardware

Two cards that look like they don't belong together

The core idea: the V100 has lots of memory and bandwidth, but little compute and no modern formats (no BF16, no FP8, no INT8 on its tensor cores, FP16 only). The 4090 has more than twice the compute and real FP8, but only 24 GB. Together they give 56 GB with almost equal bandwidth. The trick is to treat them asymmetrically: every change that treated them differently paid off.

The motherboard is the first trap. On our main PC (Gigabyte X670E AORUS MASTER) the V100 never worked: its BAR1 is fixed at 32 GB and the firmware offers at most 0.25 GB of 64-bit prefetchable window. We tried everything: CPU slot, 4090 removed, CSM off, Above 4G and ReBAR on, latest BIOS. On the X570 Taichi the full 32 GB BAR1 is assigned (verified in dmesg). Before buying a V100, make sure your motherboard can map it.
03 BIOS

Three settings, before you install the V100

  1. Above 4G Decoding: on. Without it the V100 stops the machine from booting, without even an error code.
  2. Re-Size BAR: on. The 4090 has a resizable BAR (256 MB to 24 GB) and fits into whatever space is left.
  3. CSM: off (UEFI boot only).
Watch out for clear CMOS. It resets all three settings to factory defaults, and after a reset the V100 won't let the machine boot. Set them again before putting the card back in.
04 OS and drivers

Ubuntu, the right driver and the right CUDA

Ubuntu Server 24.04. Then two constraints you don't get to choose, because the V100 is at the end of NVIDIA's support.

  • Driver branch 580, not the latest. 580 is the last branch that supports Volta (LTS until 2028); from 590 on the V100 disappears. It covers the 4090 just fine. Pin it so an upgrade can't replace it.
  • CUDA 12, not 13. CUDA 13 dropped sm_70. To build for both cards use architectures 70;89.
# driver, pinned
sudo apt install nvidia-driver-580-server
sudo apt-mark hold nvidia-driver-580-server

# check: both cards visible, and the V100's full BAR1
nvidia-smi
sudo dmesg | grep -i "BAR 1"

Two services you actually need

  • Power limit by name, never by index. V100 at 150 W, 4090 at 400 W. nvidia-smi indices change when you move cards around, so the service looks them up by name.
  • Fans driven by GPU temperature, writing only to the PWM channels of the case and the V100 shroud (never the CPU fans).
# power limit, finding the card by name
for id in $(nvidia-smi --query-gpu=index,name --format=csv,noheader | awk -F', ' '/V100/{print $1}'); do
  sudo nvidia-smi -i "$id" -pl 150
done
What the 150 W cap costs. Raising the V100 from 150 to 250 W gives +4% prefill and +0.5% generation, for 6 °C more. Not worth it.
05 First engine: llama.cpp

Works out of the box, but needs tuning: four findings

llama.cpp with GGUF models, built for 70;89, is the easiest path and is still our fallback. Before we got to the final engine it taught us four things, all measured.

1. GPU indices are swapped between tools

nvidia-smi orders by PCI bus (0 = V100); CUDA orders by speed (CUDA0 = 4090, CUDA1 = V100). So --tensor-split 51,49 means 51% to the 4090.

2. Split by compute, not by memory

The default split follows VRAM (43/57), which loads the slower card more. With a layer split the cards work one after the other, so the 4090 should get more of the work.

default 43/5751/49gain
prefill at 30k949 t/s1,090 t/s+14.9%
prefill at 50k850 t/s985 t/s+15.9%
generation53.2 t/s55.5 t/s+4.3%

Going past 51 doesn't pay: at 52–53 generation drops 5%, and at 54/46 the 4090 is left with under 0.5 GB free and crashes mid-inference. Never go below 1 GiB free on the 4090.

3. On the V100, keep the KV cache in f16

Compressing the cache slows things down: the V100 has to unpack every narrow format by hand, and that kernel costs more than the bandwidth it saves (Qwen3-Coder-30B, 16k context):

KV cachegeneration
f16102.6 t/sbaseline
q8_070.5 t/s−31%
q4_056.5 t/s−45%

4. MTP speculative decoding beats everything else

Qwen3.8 models ship an MTP head that drafts the next tokens. Turned on: 24.9 → 54.8 t/s (+120%, at temperature 0). Then llama.cpp's tensor parallel (-sm tensor --tensor-split 50,50), where both cards compute every matrix together: another +19–32% in generation (57 / 51 t/s at 30k / 100k).

Where llama.cpp stops. Past 200k of context it drops to 23–46 t/s: generic kernels, a fixed 50/50 split, no attention kernel tuned for the V100. Going further meant writing code inside an engine.
06 The vLLM detour

Useful for learning, not for staying

Upstream vLLM and SGLang don't run on the V100: their kernels (FlashAttention 2, Gated DeltaNet) require Ampere or newer. There is a fork with kernels rewritten for Volta, 1Cat-vLLM. To run it together with the 4090 we had to fix the FP4 weights path: the scales were in the Volta layout and the 4090 produced garbage. After the fix the 27B FP8 reached 262k context (25.8 t/s at 259k), but on real work it stayed at 17–19 t/s.

It did teach a rule that holds for everything after: with a mixed KV cache (f16 on the V100, fp8 on the 4090) per-turn prefill went up 2.5×. Different formats, caches and roles per card, never one ratio for both.

07 NInfer: the turbo

An engine written for these two cards

NInfer is a C++/CUDA inference engine for Qwen3.x, built for the RTX 5090 and already ported to the V100 by others (on identical V100s, at 4-bit). Our fork runs it in tensor parallel across V100 + 4090, with each card on its own compute path: rank 0 is the V100 (sm_70), rank 1 the 4090. Every change below was A/B-tested before it stayed.

The work is split by compute

The MLP (the heaviest part of each layer) isn't split in half: the 4090 takes more columns, so it doesn't wait for the V100.

The MLP is copied bit for bit from Q8_0 (one scale per 32 values); attention and Gated DeltaNet stay in the official FP8. On the V100 a rewritten 8-bit GEMV reaches 660–675 GB/s, 77% of the ceiling.

08 The model

Why a dense 27B, and why 8-bit

  • Qwen3.8-27B has hybrid attention: only 16 of its 64 layers use full attention, the rest use Gated DeltaNet. The cache costs 64 KiB per token: 16 GiB at 262k. An MoE such as Qwen3-Coder-30B needs 96 KiB per token (25.7 GiB at 262k) and doesn't fit.
  • 8-bit, not less. Below 8 bits, in any uniform quantization, the model gets exact strings wrong: for code it isn't reliable. That's why we don't use the 4-bit ports, even though they're faster.
  • Quality on real work: a complete development plan (6 TDD blocks, driven by an agent) finished in 1 h 20–1 h 33 of work, end-to-end tests 25/25 re-run twice, code review 20–21 out of 25 from three independent reviewers. The same model at FP8 on vLLM: 19.
09 Daily use

One address, models swap by themselves

  • llama-swap in front of everything, on a single port: pick the model in the client and the right engine starts by itself (NInfer loads in ~75 s).
  • OpenCode as the coding agent, with an OpenAI-compatible provider pointing at llama-swap.
  • Reasoning level from the UI: model variants xhigh, medium, low, none, passed to the engine as reasoning_effort; in OpenCode you switch them with ctrl+t.
  • Context compaction on, with the threshold close to the full context: turning it off leads to errors once a session goes past 262k.
# opencode.json: reasoning variants on a local model
"qwen3.8-27b-ninfer": {
  "limit": { "context": 262144, "output": 65536 },
  "variants": {
    "xhigh":  { "reasoningEffort": "xhigh" },
    "medium": { "reasoningEffort": "medium" },
    "low":    { "reasoningEffort": "low" },
    "none":   { "reasoningEffort": "none" }
  }
}
Reasoning length varies a lot between sessions. Two runs of the same plan on the same engine produced 165k and 458k reasoning tokens, with the same final quality. Replaying the same requests on two engine builds gives the same reasoning (57.0k vs 57.5k): it isn't the engine, it's the path the conversation takes.
10 Traps

Things that cost us hours

  • BF16 on the V100. Volta has no BF16: PyTorch silently falls back to an emulated path, about 7× slower, with no error at all. Always force FP16.
  • FP8, NVFP4 and AWQ on the V100 buy memory, not speed. They're unpacked to FP16 for every multiplication. The speed gain of an FP8 checkpoint comes only from the 4090's rank.
  • Mixed cache types (e.g. K in f16 and V in q4) in llama.cpp have no CUDA kernels for sm_70, and the work silently moves to the CPU.
  • /health lies. It reports "ready" before the model really is, and the first measurement after startup should be discarded.
  • The date in the system prompt. OpenCode writes it into the prompt: at midnight it changes and the prefix cache is invalidated, so the whole context gets re-read (147k tokens in 3 min 20 s).
  • llama.cpp tensor parallel wants equal VRAM (50,50) and can't rebalance the split: if it doesn't fit, it dies at load time.
  • A clear CMOS turns off Above 4G, and the V100 stops the machine from booting.
  • Guesses are wrong, measurements aren't. More than once we "predicted" a 3% gain that turned out to be 25%, or the other way around. Every change gets an A/B before it stays.
